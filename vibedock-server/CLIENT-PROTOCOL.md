# VibeDock image client protocol, version 2

Version 2 replaces the push protocol of version 1. **The server makes the first contact, afterwards the device pulls.** HTTP pairing remains enabled for trusted home networks; the administration form displays a warning. The server can optionally send `POST /pull` to a device address inside the network established at pairing; regular polling also works behind NAT, VPN or firewalls.

| Step | Direction | Request |
| --- | --- | --- |
| 1. Pairing code | device screen | IP address and 6-digit code are shown on the display |
| 2. Invitation | server → device | `POST http://DEVICE-IP:PORT/pair` |
| 3. Image pull | device → server | `GET /api/v1/clients/{identifier}/image`, every `pollSeconds` |

## 1. Pairing code

A device that is connected to Wi-Fi but not paired shows its IP address and a random 6-digit pairing code. The code changes on every restart. After 5 wrong codes the device stops accepting pairing requests until it is restarted (answer **429**). The code limits casual pairing attempts but does not authenticate or encrypt HTTP. A network observer can capture the code and device key; an active attacker can replace the server addresses and TLS/OTA trust keys. Use HTTP pairing only on a trusted home network, or pair over USB (step 2a). The warning does not block pairing or require an extra activation setting.

## 2. Invitation (server → device)

In the administration UI (*Devices › Pair device*) the administrator enters the device IP, the pairing code and an optional name. The server accepts IP literals only, no host names.

```http
POST http://DEVICE-IP:80/pair
Content-Type: application/json
```

```json
{
  "code": "123456",
  "servers": ["http://192.168.1.10:10002", "https://vibedock.example.com"],
  "key": "<64 lowercase hexadecimal characters, generated by the server>",
  "pollSeconds": 30,
  "name": "VibeDock Office",
  "anchor": "<base64 of one DER root certificate, only with an https address>",
  "pin": "<SHA-1 fingerprint of the https server certificate, 40 lowercase hex characters>"
}
```

- `servers` are the addresses the device may pull from, in order of preference: the **internal** address (LAN) first, then the optional **external** address (for example a public host name behind a reverse proxy). Both are set in the administration UI under *Server addresses and poll interval*; `INTERNAL_URL` and `EXTERNAL_URL` provide defaults. Without any setting the internal address is derived from the host used to open the administration UI and the public port. The UI warns when that would be `localhost`.
- Addresses have the form `http(s)://HOST[:PORT]` without path, query or credentials.
- **https:** the device has no certificate store. When an https address is announced, the server connects to it, validates its chain and host name against the Java trust store and sends the root certificate of that chain as `anchor`. The device trusts only this root for https, checks host name and validity (time from NTP) and never falls back to unchecked TLS. When the server cannot reach an https address itself (typically its own public host name behind a router without NAT loopback), it takes the newest valid certificate for the host name from the Certificate Transparency log (crt.sh), loads its issuer from the address in the certificate and validates that; the result is cached for a day and refreshed daily (`vibedock.certificate-log`, `CERTIFICATE_LOG`). The device still checks host name and chain itself when it connects; it gets no `pin` then and does the full check. Every configured address is announced. When the server cannot get a certificate for an https address (not reachable from the server, self-signed, wrong host), the address goes without `anchor` and the administration shows a warning; the device then cannot use that address and keeps to the others. One https root per device.
- **TLS versions:** the VibeTV M1 connects with TLS 1.3 (Mbed TLS) and falls back to TLS 1.2 only when the server refuses 1.3; the ESP32 boards use TLS 1.2 so far. Details, memory layout and diagnostics: [vibedock-client/TLS.md](../vibedock-client/TLS.md).
- **Simple and full check:** normally the device only compares the server certificate with `pin` (no clock needed). When that fails, typically after the certificate was renewed, it does one full check against `anchor` (chain, host name, validity) and sends `X-VibeDock-Tls-Check: full`. Only on such a request the server adds `X-VibeDock-Tls-Pin` with the fingerprint of the current certificate of the external address, and the device only accepts that header over a fully verified connection. A renewed leaf or intermediate certificate therefore needs no new invitation; a change of root does. On the M1 (TLS 1.3) the simple check requires exactly the pinned certificate and the server's proof of its key (CertificateVerify) and skips chain, root and validity; when the server sends no `X-VibeDock-Tls-Pin`, the M1 pins the certificate its own full check verified.
- `key` is the device's secret. The server stores only its SHA-256 hash in `/data/clients.json` (permissions 0600).

The device checks the code. On success it stores the addresses and the key, leaves pairing mode and answers with its current Wi-Fi subnet mask:

```json
{"identifier": "vibedock-112233445566", "name": "VibeDock", "board": "vibedock-m1", "subnetMask": "255.255.255.0"}
```

| Answer | Meaning |
| --- | --- |
| **200** | paired; the server stores the device and callback network (re-pairing replaces the key and network) |
| **403** | wrong pairing code |
| **429** | too many wrong codes, restart the device |

## 2a. Setup over USB (browser → device)

Right after flashing, the administration's browser flasher (*Devices › Firmware*) can pair the device over the same USB cable instead of steps 1 and 2. The firmware reads one command per line on its serial port (115200 baud, 8N1) at any time, also while it starts or shows its setup Wi-Fi:

| Command | Answer |
| --- | --- |
| `VIBEDOCK-HELLO` | `VIBEDOCK-READY {"identifier":"vibedock-…","name":"…","version":"0.1.0","paired":false,"board":"vibedock-m1","chip":"ESP8266"}` (also sent once at every start) |
| `VIBEDOCK-SCAN` | `VIBEDOCK-NETWORKS [{"ssid":"…","rssi":-48,"open":false},…]`, the 12 strongest networks |
| `VIBEDOCK-LOG` | `VIBEDOCK-LOG ["05-14 09:41:00 Start v0.1.0 vibedock-m1, Power on",…]`, the last 24 events oldest first: starts, Wi-Fi, pairing, server answers and why a connection failed (HTTP and TLS errors). Kept in `/log.txt` across restarts; no keys or passwords. **Devices → Firmware → Display log** shows it. |
| `VIBEDOCK-SETUP {json}` | `VIBEDOCK-SETUP OK`, then the device restarts; or `VIBEDOCK-SETUP ERROR <reason>` |

The setup JSON is the invitation of step 2 without `code`, plus `ssid` and `password` of the Wi-Fi. The server creates it with `POST /admin/firmware/setup` (`{"identifier","name","board"}`, CSRF-protected; `board` is what the device reported, or the board chosen on the page for firmware that reports none): it registers the device with a new key and returns `{"pairing":{…},"warnings":[…]}`; the browser adds the Wi-Fi, which never reaches the server. Addresses on the administration's own machine (localhost) are left out; with nothing else configured the setup is refused. The device appears under *Devices* as *Waiting for first pull* and reports its address with the first authenticated pull. That contact fixes its callback origin: `X-VibeDock-Device-IP` takes precedence over the socket peer so Docker/NAT does not supply the gateway address. With no valid header, the socket peer is used. IPv4 callbacks initially use that origin's `/24`, until a newer client supplies its mask once (see below); IPv6 stays at the original IP. The origin is persisted and cannot be changed by later reports; `GET /admin/firmware/setup/{identifier}` reports that. The browser sends a line in pieces of 128 bytes with 40 ms pauses, because the device keeps a 1 kB receive buffer, and repeats a line that got no answer. The commands are only reachable over the cable, which can rewrite the whole flash anyway.

## 3. Image pull (device → server)

```http
GET /api/v1/clients/vibedock-112233445566/image
Authorization: Bearer <device key>
If-None-Match: "<ETag of the last image>"
X-VibeDock-Device-IP: 192.168.1.50
X-VibeDock-Subnet-Mask: 255.255.255.0
X-VibeDock-Footer: server
X-VibeDock-Firmware: 0.1.0
X-VibeDock-Display: 240x240
X-VibeDock-Board: vibedock-m1
```

`X-VibeDock-Device-IP` is the device's own address. The administration shows it instead of the connection's source address, which behind NAT (Docker Desktop, reverse proxies) is only a gateway. Without the header, or with an invalid value, the source address is used. Both are reporting data. For immediate `POST /pull` callbacks, a reported IP is used only inside the network fixed during HTTP pairing: the administrator-entered target IP plus the device's `subnetMask`. Once a mask has been stored, pulls cannot change that network. With no mask (older firmware or an existing registration), IPv4 defaults to the original pairing IP's `/24`; IPv6 remains fixed to the original IP. An invalid, non-contiguous or unrestricted mask binds callbacks to the exact pairing IP and produces a warning. Reports outside the permitted network remain visible, but callbacks retain the original pairing destination and port. USB-paired devices establish their callback origin with the first authenticated image pull and initially follow the same `/24` rule. USB registrations that predate this behavior learn their origin on their next authenticated pull. Unauthenticated requests cannot establish an origin. Web displays never receive callbacks. Loopback, link-local (such as `169.254.169.254`), unspecified and multicast values are ignored; the source address counts then. A reported or paired subnet mask must be at least `/16` (`255.255.0.0`); a wider one is rejected and does not use up the one-time network learning.

`X-VibeDock-Subnet-Mask` is optional. Version **0.1.0 remains supported**, without a mask or a forced firmware update. For a registration that has no stored mask (USB or older HTTP pairing), the first authenticated pull from a recognized firmware version **newer than 0.1.0** with a valid IPv4 mask replaces the `/24` fallback once. The network is calculated from the original pairing/first-contact IP, never from a later reported IP; the current reported IP must also belong to it. Invalid masks, unrecognized/old versions and unauthenticated requests do not consume this opportunity. The learned network is persisted even if nothing else changed. Further masks, including those from later firmware updates, are ignored. A mask already learned during HTTP pairing is also kept; re-pairing starts a new registration. IPv6 does not use the IPv4 mask.

`X-VibeDock-Footer: server` says that the firmware shows the IP the server draws into the image (see *Image format*). Without it the server keeps the weather/mood band, which carries the IP, at the bottom.

`X-VibeDock-Firmware` is the firmware version (`[0-9A-Za-z.+-]`, at most 40 characters, from the Git tag). The administration shows it and compares it with the firmware the server offers. A missing or invalid value counts as no version (shown as *unknown*).

`X-VibeDock-Board` is the board the firmware was built for (see *Boards*); the server stores it and installs that board's build on updates. The invitation reply and `VIBEDOCK-READY` name it as well. Firmware before it names no board and counts as the VibeTV M1, unless another board was chosen when pairing.

`X-VibeDock-Display` is the resolution of the device's screen (`<width>x<height>`). While a device is set to the default type (VibeTV M1), a reported resolution from the display type inventory selects that type; a type chosen in the administration is kept.

| Answer | Meaning |
| --- | --- |
| **200** | width × height × 2 bytes of RGB565 pixels in the resolution of the device's display type, headers `ETag`, `X-VibeDock-Image-Format: rgb565-be-<width>x<height>` (VibeTV M1: `rgb565-be-240x240`, 115 200 bytes), `X-VibeDock-Poll-Seconds` |
| **304** | image unchanged since the given `ETag` (no body) |
| **401** | unknown device or wrong key; the device was removed and returns to pairing mode |

The endpoint exists only on the public port. Unknown identifiers and wrong keys get the same **401**. The IP allowlist of `/api/v1/usage` does not apply; the device key is the authorization. The device uses the poll interval from the latest `X-VibeDock-Poll-Seconds` (10–3600 s, default 30, set in the administration UI).

**Immediate pull (server → device):** after a design is saved, the server sends `POST http://<device IP>:<port>/pull` without a body to the affected devices (the default design: every device that follows it). After a restart it sends the same request to every paired device as soon as the first usage readings are collected (at most one minute after start). The device answers **202** and pulls in its next loop; at most one such request every 5 seconds is accepted (**429** otherwise), **409** while it is not paired. The request carries nothing secret and needs no key, because the pull that follows is authenticated as usual. Devices the server cannot reach pull at their next poll.

**Force refresh:** the device action *Force refresh* in the administration sends the same request; the next pull of that device gets **200** with the full image even if it did not change, without `ETag` and with `X-VibeDock-Redraw: 1`. The firmware then draws every row instead of only the changed ones, and pulls the following image without `If-None-Match`, learning the `ETag` again. The copy for the device's status page is requested with `X-VibeDock-Preview: 1` and does not use up a pending force refresh. Firmware from before this header still loads the full image but only redraws changed rows.

**Address fallback:** the device pulls from the first address. After a failed connection it tries the next one and stays with the address that worked until it fails again.

## 3a. Update over Wi-Fi (device ← server)

Every pairing (step 2 and 2a) carries `otaKey`, the PEM public key of the server's firmware signing key (RSA 2048, created once as `ota-signing.key`/`.pub` in the data directory). The device keeps it and then sends `X-VibeDock-Ota: 1` with every pull; firmware that can update but was paired before the server sent a key sends `X-VibeDock-Ota: no-key`, and the administration asks to pair it again. When the administrator starts an update (*Update to …* on the device list, the overview or the firmware page, or *Update all*), the next pull answers with `X-VibeDock-Update: <version>`; the server also asks a reachable device to pull right away (`POST /pull`), a device it cannot reach learns it with its next regular pull. The device then fetches

```http
GET /api/v1/clients/vibedock-112233445566/firmware
Authorization: Bearer <device key>
```

which returns the firmware followed by its signature (SHA-256, PKCS#1 v1.5) and the signature length as 32-bit little endian, the format of the ESP8266 updater, plus `x-MD5` of the whole body and `X-VibeDock-Length`, its size (a reverse proxy may answer chunked without `Content-Length`). The device writes it next to the running firmware and switches over only if the signature matches its stored key and the MD5 is right; otherwise the running firmware stays and the next pull reports `X-VibeDock-Update-Error: <version>: <reason>`, shown in the administration. A device tries a failed version again only after a restart. The request ends when the device reports the offered version. Pairing again replaces the key; unpairing removes it. Firmware without update support sends no `X-VibeDock-Ota` and is updated once over USB.

## 3b. Web displays (browser or program → server)

A web display is created in the administration and has no firmware. It fetches with the secret from its links, on the public port only:

| Request | Answer |
| --- | --- |
| `GET /web/<secret>` | HTML page that shows the image full screen (black background, scaled to fit) and fetches it again every reload interval |
| `GET /web/<secret>/image.png` | the image as PNG in the resolution of the web display's type, `Cache-Control: no-store` |

The secret is 64 lowercase hex characters; unknown secrets get **404**, other methods **405**, the administration port **404**. Each image fetch counts as a pull for the status in the administration. Where a device's image shows `IP: …`, a web display's image shows `VibeDock server v<version>`.

## Boards

One firmware source builds for several boards (PlatformIO environments in `vibedock-client/firmware/platformio.ini`, the server's inventory in `Board.java`):

| Board id | Hardware | Chip | Display type |
| --- | --- | --- | --- |
| `vibedock-m1` | VibeTV M1 (ESP-12E, 1.54" ST7789) | ESP8266 | 240×240 |
| `esp32-cyd` | "Cheap Yellow Display" ESP32-2432S028R (2.8" ILI9341) | ESP32 | 320×240 |
| `lilygo-t-display` | LilyGO T-Display (1.14" ST7789) | ESP32 | 135×240 |
| `lilygo-t-display-s3` | LilyGO T-Display-S3 (1.9" ST7789, 8-bit parallel) | ESP32-S3 | 170×320 |
| `waveshare-s3-lcd-169` | Waveshare ESP32-S3-LCD-1.69 (ST7789V2) | ESP32-S3 | 240×280 |
| `esp32-c3-st7789` | ESP32-C3 with a 1.3" ST7789 (SCL 4, SDA 6, DC 2, RES 3, BLK 10) | ESP32-C3 | 240×240 |

Each build yields `flash.bin`, written at `0x0` over USB (on ESP32 chips bootloader, partition table and app merged), and `firmware.bin`, the app for updates over Wi-Fi. The update format is the same on all chips (step 3a); on ESP32 chips the firmware checks the signature with mbedTLS itself before it activates the new app. https on ESP32 chips always uses the full check against the root from pairing (no SHA-1 fingerprint). The device's own screens are laid out for 240×240 and scaled to fit other panels; server images arrive in the panel's resolution.

## Image format

Pixels are sent row by row from the top left: `width` pixels per row, `height` rows as named in `X-VibeDock-Image-Format`, two bytes per pixel, most significant byte first, 5 red, 6 green and 5 blue bits. No compression. The administration UI shows a PNG of the same pixels.

**Display types:** the administration keeps an inventory of display resolutions (VibeTV M1 240×240 as default, 240×280, 240×320, 320×240, 170×320, 135×240, 128×160) and renders each device's design for its type: the first usage bands that fit its height (full bands 92 px, compact rows 46 px, shrinking to 88/44 px where needed; the M1 holds two full bands, one full and two compact or four compact ones); split bands show only their first source below 200 px width. Current firmware accepts any size from 16 to 480 px per side and scales it nearest-neighbour to its whole screen, so a wrong type still fills the screen, just distorted; with the right type the image is drawn 1:1.

**The server draws the whole image, the device IP included.** It writes `IP: <X-VibeDock-Device-IP>` into the bottom-left corner of the weather/mood band (20 rows, columns 0–149), wherever the design places that band. Current firmware draws the image over the whole screen and shows its own IP footer (rows 220–239) only on its own screens: setup, pairing, `Server unreachable`, `Updates missing`. When its IP changes the device pulls a new image right away.

Older firmware (no `X-VibeDock-Footer` header) still draws its IP footer over rows 220–239, columns 0–149; for it the server keeps the weather/mood band at the bottom, where the server's IP corner lies under the device's.

## Status in the administration UI

| Status | Meaning |
| --- | --- |
| `Waiting for first pull` | paired, no pull yet |
| `Connected` | last pull within three poll intervals |
| `Updates missing` | no pull for more than three poll intervals |
| `Not connected yet` / `Not connected` | web display: no fetch yet / none for three reload intervals (its page is closed) |

`Remove device` deletes the device; its next pull gets **401** and it returns to pairing mode. The device shows `Updates missing` itself after three poll intervals without a successful pull.

## Validation

Pairing (correct and wrong code), key hashing, pull authentication, `ETag`/**304**, removal and port separation are covered by Java tests with a local device simulator. The ESP8266 firmware in `vibedock-client/` implements version 2 and runs on real devices.
