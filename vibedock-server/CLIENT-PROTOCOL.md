# VibeDock image client protocol, version 2

Version 2 replaces the push protocol of version 1. **The server makes the first contact, afterwards the device pulls.** HTTP pairing remains enabled for trusted home networks; the administration form displays a warning. The server can optionally send `POST /pull` to a device address inside the network established at pairing; regular polling also works behind NAT, VPN or firewalls.

| Step | Direction | Request |
| --- | --- | --- |
| 1. Pairing code | device screen | IP address and 6-digit code are shown on the display |
| 2. Invitation | server → device | `POST http://DEVICE-IP:PORT/pair` |
| 3. Image pull | device → server | `GET /api/v1/clients/{identifier}/image`, every `pollSeconds` |

## 1. Pairing code

A device that is connected to Wi-Fi but not paired shows its IP address and a random 6-digit pairing code. The code changes on every restart. After 5 wrong codes the device stops accepting pairing requests until it is restarted (answer **429**). The code limits casual pairing attempts but does not authenticate or encrypt HTTP. A network observer can capture the code and device key; an active attacker can replace the server addresses and TLS/OTA trust keys. Use HTTP pairing only on a trusted home network, or pair over USB (step 2a). The warning does not block pairing or require an extra activation setting.

## 2. Invitation (server → device)

In the administration UI (*Devices › Pair device*) the administrator enters the device IP, the pairing code and an optional name. The server accepts IP literals only, no host names.

```http
POST http://DEVICE-IP:80/pair
Content-Type: application/json
```

```json
{
  "code": "123456",
  "servers": ["http://192.168.1.10:10002", "https://vibedock.example.com"],
  "key": "<64 lowercase hexadecimal characters, generated by the server>",
  "pollSeconds": 30,
  "name": "VibeDock Office",
  "anchor": "<base64 of one DER root certificate, only with an https address>",
  "pin": "<SHA-1 fingerprint of the https server certificate, 40 lowercase hex characters>"
}
```

- `servers` are the addresses the device may pull from, in order of preference: the **internal** address (LAN) first, then the optional **external** address (for example a public host name behind a reverse proxy). Both are set in the administration UI under *Server addresses and poll interval*; `INTERNAL_URL` and `EXTERNAL_URL` provide defaults. Without any setting the internal address is derived from the host used to open the administration UI and the public port. The UI warns when that would be `localhost`.
- Addresses have the form `http(s)://HOST[:PORT]` without path, query or credentials.
- **https:** the device has no certificate store. The server validates the HTTPS chain and hostname against the Java trust store and sends the root as `anchor`; a successful live inspection can also supply the leaf certificate's `pin`. The device never falls back to unchecked TLS. The server's lookup routes and root-only certificate-log fallback are described under [Server-side certificate inspection](#server-side-certificate-inspection). Every configured address is announced. If no suitable root is available (unreachable, untrusted certificate or wrong hostname), the administration warns and the device cannot use that HTTPS address. One HTTPS root per device.
- **TLS versions:** the VibeTV M1 connects with TLS 1.3 (Mbed TLS) and falls back to TLS 1.2 only when the server refuses 1.3; the ESP32 boards use TLS 1.2 so far. Details, memory layout and diagnostics: [vibedock-client/TLS.md](../vibedock-client/TLS.md).
- **Simple and full check:** normally the device only compares the server certificate with `pin` (no clock needed). When that fails, typically after the certificate was renewed, it does one full check against `anchor` (chain, host name, validity) and sends `X-VibeDock-Tls-Check: full`. Only on such a request the server adds `X-VibeDock-Tls-Pin` with the fingerprint of the current certificate of the external address, and the device only accepts that header over a fully verified connection. A renewed leaf or intermediate certificate therefore needs no new invitation; a change of root does. On the M1 (TLS 1.3) the simple check requires exactly the pinned certificate and the server's proof of its key (CertificateVerify) and skips chain, root and validity; when the server sends no `X-VibeDock-Tls-Pin`, the M1 pins the certificate its own full check verified.
- `key` is the device's secret. The server stores only its SHA-256 hash in `/data/clients.json` (permissions 0600).

The device checks the code. On success it stores the addresses and the key, leaves pairing mode and answers with its current Wi-Fi subnet mask:

```json
{"identifier": "vibedock-112233445566", "name": "VibeDock", "board": "vibedock-m1", "subnetMask": "255.255.255.0"}
```

| Answer | Meaning |
| --- | --- |
| **200** | paired; the server stores the device and callback network (re-pairing replaces the key and network) |
| **403** | wrong pairing code |
| **429** | too many wrong codes, restart the device |

## 2a. Setup over USB (browser → device)

Right after flashing, the administration's browser flasher (*Devices › Firmware*) can pair the device over the same USB cable instead of steps 1 and 2. The firmware reads one command per line on its serial port (115200 baud, 8N1) at any time, also while it starts or shows its setup Wi-Fi:

| Command | Answer |
| --- | --- |
| `VIBEDOCK-HELLO` | `VIBEDOCK-READY {"identifier":"vibedock-…","name":"…","version":"0.1.0","paired":false,"board":"vibedock-m1","chip":"ESP8266"}` (also sent once at every start) |
| `VIBEDOCK-BATTERY` | `VIBEDOCK-BATTERY {"supported":true,"voltageMv":3900,"estimatedPercent":80,"chargeSignal":"inactive","present":null}` (illustrative reading). Supported on `waveshare-s3-touch-lcd-154` and, without a charging signal (`chargeSignal:"unknown"`), on `waveshare-c6-touch-lcd-169`; other boards return `supported:false`, null measurements and `chargeSignal:"unknown"`. |
| `VIBEDOCK-SCAN` | `VIBEDOCK-NETWORKS [{"ssid":"…","rssi":-48,"open":false},…]`, the 12 strongest networks. While the display keeps trying a saved network out of reach, it pauses those attempts for the scan and resumes them afterwards. |
| `VIBEDOCK-LOG` | `VIBEDOCK-LOG ["05-14 09:41:00 Start v0.1.0 vibedock-m1, Power on",…]`, the last 24 events oldest first: starts, Wi-Fi, pairing, server answers and why a connection failed (HTTP and TLS errors). Kept in `/log.txt` across restarts; no keys or passwords. **Devices → Troubleshooting → Read log over USB** shows it. |
| `VIBEDOCK-SETUP {json}` | `VIBEDOCK-SETUP OK`, then the device restarts; or `VIBEDOCK-SETUP ERROR <reason>` |

On `waveshare-s3-touch-lcd-154`, `VIBEDOCK-READY` additionally contains a `battery` object with the same fields. Battery readings are optional diagnostics; they do not change pairing or device authentication. `present` stays null: the charging circuit cannot reliably identify a missing cell while USB is connected. The level is a coarse voltage-only estimate (null outside the expected range), not a fuel gauge; a voltage or active charging signal does not prove a battery is fitted. An inactive signal does not mean full. `chargeSignal` is `unstable` when the short sample contains both levels; slower cycling may not be detected. During a TLS handshake only HELLO and LOG are handled; send BATTERY again afterwards.

The setup JSON is the invitation of step 2 without `code`, plus `ssid` and `password` of the Wi-Fi. The server creates it with `POST /admin/firmware/setup` (`{"identifier","name","board"}`, CSRF-protected; `board` is what the device reported, or the board chosen on the page for firmware that reports none): it registers the device with a new key and returns `{"pairing":{…},"warnings":[…]}`; the browser adds the Wi-Fi, which never reaches the server. Addresses on the administration's own machine (localhost) are left out; with nothing else configured the setup is refused. The device appears under *Devices* as *Waiting for first pull* and reports its address with the first authenticated pull. That contact fixes its callback origin: `X-VibeDock-Device-IP` takes precedence over the socket peer so Docker/NAT does not supply the gateway address. With no valid header, the socket peer is used. IPv4 callbacks initially use that origin's `/24`, until a newer client supplies its mask once (see below); IPv6 stays at the original IP. The origin is persisted and cannot be changed by later reports; `GET /admin/firmware/setup/{identifier}` reports that. The browser sends a line in pieces of 128 bytes with 40 ms pauses, because the device keeps a 1 kB receive buffer, and repeats a line that got no answer. The commands are only reachable over the cable, which can rewrite the whole flash anyway.

### Optional sound metadata

An audio-capable client explicitly requests `X-VibeDock-Audio: 1` on its ordinary authenticated image pull.
Only then the server sends `X-VibeDock-Quota`, on both 200 and 304 replies. Requests without that exact capability
and `X-VibeDock-Preview: 1` requests get **no** quota header. Existing clients and servers keep working unchanged.
The request is a capability opt-in, not authentication; the existing device key still protects the endpoint.

The value is `v1;<window-id>:<remaining>;...`, or just `v1` when no valid windows are available. Each window id
is the first twelve lowercase hex characters of SHA-256 of its source id followed by `f` (five-hour window)
or `w` (weekly/single long window). Remaining is an integer in basis points, 0–10000 (10000 = 100%). There
are at most 20 windows and 402 ASCII bytes, below the client's 420-byte parser bound. Only sources in the layout
fitted to that display are sent, once each, with fresh `ok`/`partial` readings and valid, non-expired windows.
No labels, credentials or provider tokens are included. Slideshow images keep the same configured-source metadata.

The client validates the complete header before replacing its in-memory baseline. Initial and previously unseen windows
are silent; each increase or decrease relative to the previous reading sounds once, without thresholds. Reaching
10000 or 0 is a full/empty event (using the rise/fall melody instead of duplicating it). Same-kind changes in one
response share a melody. Unchanged values are silent, including repeated 304 replies. Missing metadata resets
the baseline; malformed data is ignored. Temporarily omitted windows in a valid `v1` header retain their
last comparison values, so an expired window followed by a full refill still sounds. The cache holds at most
20 windows: current entries take priority over absent ones, which may be evicted when capacity is reached. Preview pulls neither consume nor advance it. All this state is local
to the display, so restarts establish a new silent baseline rather than replaying old notifications.

## 3. Image pull (device → server)

```http
GET /api/v1/clients/vibedock-112233445566/image
Authorization: Bearer <device key>
If-None-Match: "<ETag of the last image>"
X-VibeDock-Device-IP: 192.168.1.50
X-VibeDock-Subnet-Mask: 255.255.255.0
X-VibeDock-Footer: server
X-VibeDock-Firmware: 0.1.0
X-VibeDock-Display: 240x240
X-VibeDock-Board: vibedock-m1
```

`X-VibeDock-Device-IP` is the device's own address. The administration shows it instead of the connection's source address, which behind NAT (Docker Desktop, reverse proxies) is only a gateway. Without the header, or with an invalid value, the source address is used. Both are reporting data. For immediate `POST /pull` callbacks, a reported IP is used only inside the network fixed during HTTP pairing: the administrator-entered target IP plus the device's `subnetMask`. Once a mask has been stored, pulls cannot change that network. With no mask (older firmware or an existing registration), IPv4 defaults to the original pairing IP's `/24`; IPv6 remains fixed to the original IP. An invalid, non-contiguous or unrestricted mask binds callbacks to the exact pairing IP and produces a warning. Reports outside the permitted network remain visible, but callbacks retain the original pairing destination and port. USB-paired devices establish their callback origin with the first authenticated image pull and initially follow the same `/24` rule. USB registrations that predate this behavior learn their origin on their next authenticated pull. Unauthenticated requests cannot establish an origin. Web displays never receive callbacks. Loopback, link-local (such as `169.254.169.254`), unspecified and multicast values are ignored; the source address counts then. A reported or paired subnet mask must be at least `/16` (`255.255.0.0`); a wider one is rejected and does not use up the one-time network learning.

`X-VibeDock-Subnet-Mask` is optional. Version **0.1.0 remains supported**, without a mask or a forced firmware update. For a registration that has no stored mask (USB or older HTTP pairing), the first authenticated pull from a recognized firmware version **newer than 0.1.0** with a valid IPv4 mask replaces the `/24` fallback once. The network is calculated from the original pairing/first-contact IP, never from a later reported IP; the current reported IP must also belong to it. Invalid masks, unrecognized/old versions and unauthenticated requests do not consume this opportunity. The learned network is persisted even if nothing else changed. Further masks, including those from later firmware updates, are ignored. A mask already learned during HTTP pairing is also kept; re-pairing starts a new registration. IPv6 does not use the IPv4 mask.

`X-VibeDock-Footer: server` says that the firmware shows the IP the server draws into the image (see *Image format*). Without it the server keeps the weather/mood band, which carries the IP, at the bottom.

`X-VibeDock-Firmware` is the firmware version (`[0-9A-Za-z.+-]`, at most 40 characters, from the Git tag). The administration shows it and compares it with the firmware the server offers. A missing or invalid value counts as no version (shown as *unknown*).

`X-VibeDock-Board` is the board the firmware was built for (see *Boards*); the server stores it and installs that board's build on updates. The invitation reply and `VIBEDOCK-READY` name it as well. Firmware before it names no board and counts as the VibeTV M1, unless another board was chosen when pairing.

`X-VibeDock-Display` is the resolution of the device's screen (`<width>x<height>`). While a device is set to the default type (VibeTV M1), a reported resolution from the display type inventory selects that type; a type chosen in the administration is kept.

| Answer | Meaning |
| --- | --- |
| **200** | width × height × 2 bytes of RGB565 pixels in the resolution of the device's display type, headers `ETag`, `X-VibeDock-Image-Format: rgb565-be-<width>x<height>` (VibeTV M1: `rgb565-be-240x240`, 115 200 bytes), `X-VibeDock-Poll-Seconds` |
| **304** | image unchanged since the given `ETag` (no body) |
| **401** | unknown device or wrong key; the device was removed and returns to pairing mode |

The endpoint exists only on the public port. Unknown identifiers and wrong keys get the same **401**. The IP allowlist of `/api/v1/usage` does not apply; the device key is the authorization. The device uses the poll interval from the latest `X-VibeDock-Poll-Seconds` (10–3600 s, default 30, *Fallback poll interval* in the administration UI); current firmware pulls when `X-VibeDock-Next-Pull` says instead (section 3h) and uses the poll interval only as a fallback. While a display shows a slideshow, it gets the time of one photo when that is shorter (at least 10 s). In a slideshow, a swipe (section 3d) shows the next or previous photo instead of changing the colour scheme.

**Immediate pull (server → device):** after a design is saved, the server sends `POST http://<device IP>:<port>/pull` without a body to the affected devices (the default design: every device that follows it). After a restart it sends the same request to every paired device as soon as the first usage readings are collected (at most one minute after start). The device answers **202** and pulls in its next loop; at most one such pull every 5 seconds: a request within that pause (also **202**) is pulled when it is over (firmware before 0.2.0 answers **429** and pulls at its next poll), **409** while it is not paired. The request carries nothing secret and needs no key, because the pull that follows is authenticated as usual. Devices the server cannot reach pull at their next poll.

**Force refresh:** the device action *Force refresh* in the administration sends the same request; the next pull of that device gets **200** with the full image even if it did not change, without `ETag` and with `X-VibeDock-Redraw: 1`. The firmware then draws every row instead of only the changed ones, and pulls the following image without `If-None-Match`, learning the `ETag` again. The copy for the device's status page is requested with `X-VibeDock-Preview: 1` and does not use up a pending force refresh. Firmware from before this header still loads the full image but only redraws changed rows.

**Address fallback:** the device pulls from the first address. After a failed connection it tries the next one and stays with the address that worked until it fails again.

## 3a. Update over Wi-Fi (device ← server)

Every pairing (step 2 and 2a) carries `otaKey`, the PEM public key of the server's firmware signing key (RSA 2048, created once as `ota-signing.key`/`.pub` in the data directory). The device keeps it and then sends `X-VibeDock-Ota: 1` with every pull; firmware that can update but was paired before the server sent a key sends `X-VibeDock-Ota: no-key`, and the administration asks to pair it again. When the administrator starts an update (*Update to …* on the device list, the overview or the firmware page, or *Update all*), the next pull answers with `X-VibeDock-Update: <version>`; the server also asks a reachable device to pull right away (`POST /pull`), a device it cannot reach learns it with its next regular pull. The device then fetches

```http
GET /api/v1/clients/vibedock-112233445566/firmware
Authorization: Bearer <device key>
```

which returns the firmware followed by its signature (SHA-256, PKCS#1 v1.5) and the signature length as 32-bit little endian, the format of the ESP8266 updater, plus `x-MD5` of the whole body and `X-VibeDock-Length`, its size (a reverse proxy may answer chunked without `Content-Length`). The device writes it next to the running firmware and switches over only if the signature matches its stored key and the MD5 is right; otherwise the running firmware stays and the next pull reports `X-VibeDock-Update-Error: <version>: <reason>`, shown in the administration. A device tries a failed version again only after a restart. The request ends when the device reports the offered version. Pairing again replaces the key; unpairing removes it. Firmware without update support sends no `X-VibeDock-Ota` and is updated once over USB.

## 3b. Web displays (browser or program → server)

A web display is created in the administration and has no firmware. It fetches with the secret from its links, on the public port only:

| Request | Answer |
| --- | --- |
| `GET /web/<secret>` | HTML page that shows the image full screen (black background, scaled to fit) and fetches it again every reload interval |
| `GET /web/<secret>/image.png` | the image as PNG in the resolution of the web display's type, `Cache-Control: no-store`; with `?w=<width>&h=<height>&r=<pixel ratio>` (CSS pixels of the window) drawn at that resolution, *Fit the browser* in the window's shape |
| `GET /web/<secret>/state` | `{"tag":"…"}`, a tag of the current image; the page polls it every 3 s and loads a new image when it changes |
| `POST /web/<secret>/swipe?direction=next\|previous\|toggle` | a swipe on the page: the next or previous colour scheme, in a running slideshow the photo; `toggle` (double tap): the slideshow on or off (as 3d); **204** |
| `GET /web/<secret>/icon.png` | the home screen icon (180 × 180) |

The secret is 64 lowercase hex characters; unknown secrets get **404**, other methods **405**, the administration port **404**. Each image fetch counts as a pull for the status in the administration. Where a device's image shows `IP: …`, a web display's image shows `VibeDock server v<version>`.

## 3c. Device log (device → server)

The administration can ask a display for its log (*Devices › Logs › Read log over the network*). The server then
answers the display's next image pull (200 or 304) with `X-VibeDock-Send-Log: <request id>` (32 lowercase hex
characters, valid for 10 minutes and one upload; a new request replaces an open one) and asks a reachable display to
pull right away (`POST /pull`). The display then sends its log:

```
POST /api/v1/clients/{identifier}/log
Authorization: Bearer <device key>
X-VibeDock-Log-Request: <request id>
Content-Type: text/plain; charset=utf-8

<one event per line, oldest first>
```

| Answer | Meaning |
| --- | --- |
| **204** | saved as a log of the display with the source `net` (the last 10 per display are kept) |
| **401** | unknown device or wrong key |
| **409** | no open request with this id (wrong, used or expired) |
| **413** | larger than 64 kB |

Only the public port accepts it, and only `POST`. The server removes key-like values and web display links from the
lines, and keeps at most 500 lines of 400 characters. The same is saved for logs the browser reads over USB on the
Troubleshooting page. Firmware up to 0.1.1 does not know the header and keeps sending its log only over USB.

## 3d. Touch gestures (device → server)

Displays with a touch panel send a swipe left or right with their next image pull, which follows right away:
`X-VibeDock-Gesture: scheme-next` (left) or `scheme-previous` (right). The server switches the display's colour scheme
to the next or previous one in its list (wrapping around), stores it as the display's own design (also when it
followed the default until then) and answers with the new image. Other values are ignored, and so is the header on
older servers. Swipes up and down change the backlight on the display only (10–100 %, kept across restarts).
A double tap sends `X-VibeDock-Gesture: photos-toggle`: the server starts the slideshow of the display's design when
it does not run and stops it when it does, whatever its schedule or the editor's switch say, for that display until
the next double tap or a restart of the server; a design without photos stays as it is.
A circle drawn with one finger sends `X-VibeDock-Gesture: turn-clockwise` or `turn-counterclockwise`: the server sets
the display's orientation (3e) to the next one in that direction, by a quarter turn on square panels and otherwise
between upright and flipped, and answers this pull with the new `X-VibeDock-Orientation`. The firmware counts a touch
as a circle when its points go round their centre by at least 300° on an average radius of at least 35 pixels and end
near their start.

## 3e. Orientation (server → device)

Every board except the VibeTV M1 (its case decides how it stands) gets `X-VibeDock-Orientation` with every 200 and
304 answer, set with *Orientation* on the device card: `upright`, `flipped` (180 degrees), and on square panels also
`rotated-90` and `rotated-270` (clockwise). The display turns its panel accordingly, so the image, its
own screens and the swipes are turned as well; it stores the setting and draws the next image completely. The image
itself is the same in every case. Firmware that does not know a value keeps its orientation: firmware before 0.2.0
ignores the header, firmware before the quarter turns keeps its last `upright`/`flipped` state for `rotated-90` and
`rotated-270`. The server stores the turn as `rotation` and keeps `flipped` set for 180 degrees, so an older server
reads such a device as flipped.

## 3f. Diagnosis (device → server)

Firmware newer than 0.1.1 sends with every request (image, firmware and log) what it knows about its own start:

```
X-VibeDock-Diag: boot=1a2b3c4d;up=754;heap=21344;min=18012;rssi=-61;drops=0;start=crash;reset=4;prev=0f0e0d0c;phase=image;prevup=5400;prevheap=9120;prevmin=4100;prevrssi=-70;prevdrops=2
```

| Key | Meaning |
| --- | --- |
| `boot` | random id of this start (8 hex digits); one start counts once, however often it is reported |
| `up` | seconds since this start (device run time, not a clock time) |
| `heap`, `min` | free heap at the last pull and its lowest value seen (ESP8266: at the pulls; ESP32: the platform's minimum) |
| `rssi`, `drops` | Wi-Fi signal at the last pull (0 when not connected) and how often the connection was lost |
| `start` | `power-on`, `update`, `setup`, `factory-reset`, `external` (button or USB reset), `crash`, `watchdog`, `brownout`, `software` (a restart the firmware did not plan), `deep-sleep`, `other` |
| `reset` | the platform's reset code (ESP8266: `rst_info` reason or the crash record's; ESP32: `esp_reset_reason()`) |
| `prev`, `phase`, `prev…` | the run before as kept in memory that survives a reset (not a power cut): its boot id, its last phase (`start`, `wifi`, `connect`, `tls`, `image`, `draw`, `config`, `log`, `ota`, `idle`, `portal`) and its values; missing when unknown |
| `panic` | after a crash of the run before: its code addresses in hex, the instruction first, comma-separated (at most 6; ESP32 with Arduino core 3: the backtrace, core 2: the return address; ESP8266: `epc1`) |
| `cause`, `fault` | with `panic`, where the chip gives them: the exception cause (RISC-V `mcause`, Xtensa and ESP8266 `EXCCAUSE`) and the faulting address in hex |
| `abort` | with `panic` after `abort()` or a failed assert (ESP-IDF 5): its text, at most 60 characters of `A-Za-z0-9 .:_/()-` |

The firmware writes the record to RTC memory, not to flash: when the phase changes and once per pull. The log's start
line carries the same (`Start v… <board>: boot=… reset=… start=… prev=… phase=… up=… heap=…/…; <reset text>`), so a log
read over USB names its starts too. The server checks every value, keeps the current values in memory and each new
start per display (the last 20); a header from older firmware is simply absent. The crash addresses come from the panic
handler, kept in RTC memory as well; they are decoded with the ELF of that firmware (`addr2line -pfiaC -e firmware.elf
<addresses>`, see `vibedock-client/FLASHING.md`, *Decoding a crash*). The full backtrace stays on the serial port.

## 3g. Battery power saving (server → device, experimental)

Boards with a battery connection whose chip has its own USB (Waveshare 1.54, 1.47, C6 1.69, S3 1.69, LilyGO
T-Display-S3; `Board.batteryPowerSaving`, `VIBEDOCK_BATTERY` in platformio.ini) get `X-VibeDock-Power-Saving` with
every 200 and 304 answer: `battery` when *Battery power saving* is switched on on the device card, otherwise `off`.
The display stores the setting. With `battery` it saves power while it runs on its battery: no USB host sends frames
(the start-of-frame counter of the chip's USB serial/JTAG unit) and, on the 1.54, the charging signal is inactive; two
readings 5 s apart. Then it switches on Wi-Fi modem sleep, runs its CPU at 80 MHz and dims the backlight to 10 % after
a minute without touch or volume button; the next touch only wakes it. A USB host (or charging on the 1.54) ends it,
as does `off`. A charger without data lines counts as battery operation. The status page, `VIBEDOCK-BATTERY` and the
`battery` object of `VIBEDOCK-HELLO` show `powerSource` (`battery`, `usb`) and `powerSaving` (`off`, `allowed`,
`active`). Firmware before this ignores the header.

On its battery such a display also sends `X-VibeDock-Power: battery` with its pulls, on the 1.54 with its level
(`battery;level=60`, the voltage estimate in steps of 20), whether power saving is on or not; on USB it sends nothing.
The server then draws a battery icon at the top right of the first usage band (left of a status, in the title bar of
window themes), filled to the level, red below 20 %. It keeps the report in memory until the next pull, so the
preview on the device card shows the same. The display pulls right away when its power source changes.

The update format is the same on all chips (step 3a); on ESP32 chips the firmware checks the signature with mbedTLS itself before it activates the new app. https on ESP32 chips always uses the full check against the root from pairing (no SHA-1 fingerprint). The device's own screens are laid out for 240×240 and scaled to fit other panels; server images arrive in the panel's resolution.

## 3h. Next pull (server → device)

Every answer to an image pull, **200** and **304** alike, carries `X-VibeDock-Next-Pull: <seconds>; state=<current|pending>`:
when the picture of this display can change next, so the display pulls then instead of every poll interval.

- `state=current`: the sources the display shows (its layout fitted to its display type) have been asked; a **304**
  really means nothing changed. The seconds run to the earliest of: the next poll of one of those sources plus the
  time a collection takes (smoothed, about 2 s) and 2 s; the moment one of their readings turns stale; the next
  photo of a running slideshow; the start or end of a scheduled one.
- `state=pending`: one of those sources is due or being asked and its reading is not published yet. The seconds run
  to when the collection should be done; repeated `pending` answers wait at least 2, 5, 10, then 30 s, so a slow
  provider cannot make the display pull every second. A failed poll or HTTP 429 is done as well: the next answer is
  `current` with the time of the next try.
- At most 600 s for displays that took an immediate pull (`POST /pull`, section 2) within the last day, so design
  changes still reach them at once; at most 120 s for the others (behind NAT, only through the external address),
  which see design changes with their next pull. At least 2 s.

All sources are polled together on the full minute and published at the end of that collection, so several providers
do not make a display pull more often than once a minute (plus pending answers). The server log adds the announced
time to each image transfer line (`next=58 s (current)`).

Firmware that follows it sends `X-VibeDock-Schedule: 1` with its screen pulls; the server then expects its next pull at
the announced time (section *Status*). It still uses `X-VibeDock-Poll-Seconds` until the first answer, after failed
pulls, for immediate retries and when the header is missing (older servers). Older firmware ignores the header and
keeps pulling every poll interval. The display's status page shows the next pull. Weather refreshes in the background
at most every 15 minutes and appears with the next pull after that, so it can show up to one wait later than before.

## Image format

Pixels are sent row by row from the top left: `width` pixels per row, `height` rows as named in `X-VibeDock-Image-Format`, two bytes per pixel, most significant byte first, 5 red, 6 green and 5 blue bits. No compression. The administration UI shows a PNG of the same pixels.

**Display types:** the administration keeps an inventory of display resolutions (VibeTV M1 240×240 as default, 240×280, 240×320, 320×240, 170×320, 172×320, 135×240, 128×160) and renders each device's design for its type: the first usage bands that fit its height (full bands 92 px, compact rows 46 px, shrinking to 88/44 px where needed; the M1 holds two full bands, one full and two compact or four compact ones); split bands show only their first source below 200 px width. Current firmware accepts any size from 16 to 480 px per side and scales it nearest-neighbour to its whole screen, so a wrong type still fills the screen, just distorted; with the right type the image is drawn 1:1.

**The server draws the whole image, the device IP included.** It writes `IP: <X-VibeDock-Device-IP>` into the bottom-left corner of the weather/mood band (20 rows, columns 0–149), in the theme's font and text colour straight over the background, wherever the design places that band. When it does not fit before the mood or a temperature in the same row (narrow panels), the text gets smaller, then loses `IP: `, then its leading segments (`…123.193`): the last segments tell displays apart. Current firmware draws the image over the whole screen and shows its own IP footer (rows 220–239) only on its own screens: setup, pairing, `Server unreachable`, `Updates missing`. When its IP changes the device pulls a new image right away.

Older firmware (no `X-VibeDock-Footer` header) still draws its IP footer over rows 220–239, columns 0–149; for it the server keeps the weather/mood band at the bottom, where the server's IP corner lies under the device's.

### Optional delta images (v1)

New firmware sends `X-VibeDock-Delta: 1` on screen image pulls, together with its actual
`X-VibeDock-Display` size. This does not change the pairing protocol. Old firmware receives full images;
new firmware works with old servers. Web displays keep PNG. Device status-page preview pulls do not opt in.

The server always renders a complete RGB565 image and computes its ETag from those full pixels, even when it
sends only a delta. It retains up to three complete images per device, for ten minutes, with global limits of
128 devices and 12 MiB of pixel data (plus bounded metadata). Cache entries are in RAM only. Eviction or restart
simply causes a full image. A missing/unknown base ETag, different dimensions, a slideshow photo, preview,
forced redraw or a delta at least as large as the full image also uses the existing full format.

A delta **200** response has:

| Header | Value |
| --- | --- |
| `X-VibeDock-Image-Format` | `rgb565-delta-be-<width>x<height>`; exact panel size, never scaled |
| `X-VibeDock-Base` | Exact ETag from the device's conditional request |
| `ETag` | ETag of the complete resulting image |
| `X-VibeDock-Length` | Exact delta body length, including terminator; also used when a proxy removes Content-Length |
| `X-VibeDock-Payload` | Eight lowercase hex digits: FNV-1a-32 of all body bytes |
| `X-VibeDock-Check` | Eight lowercase hex digits: FNV-1a-32 of the resulting row hashes, serialized as big-endian uint32 values |

All integers in the body are unsigned, big-endian. Each section is:

```
y:u16, rowCount:u16, x:u16, width:u16
rowCount × rowHash:u32
rowCount × width × RGB565 pixel:u16
```

A final `y = 0xffff` (two bytes only) ends the body. No trailing bytes are allowed. Sections contain ascending,
disjoint groups of rows; each row appears at most once. Coordinates, nonzero counts and widths must be within
the panel. Adjacent changed rows with the same changed horizontal extent are grouped together. Other unchanged
rows and pixels are omitted. Row hashes cover the **whole uncorrected new row**, using `client_policy::rowHash`:
FNV-1a-32 (offset `2166136261`, multiplier `16777619`, modulo 2^32), mapping a zero result to 1. The payload and
row-table checks use ordinary FNV-1a without this zero mapping. These are error checks, not authentication.

The firmware accepts a delta only over a complete, unscaled image with a matching base ETag and valid row
state. Local setup/error screens, orientation or colour correction invalidate this basis. It reads one span
at a time into the existing row buffer, applies colour correction and updates the panel. Volume overlays are
local to the device; changes also update their saved background pixels. No full framebuffer is allocated.

The new ETag is committed only after the exact length, terminator, payload checksum and row-table checksum
have passed. After any rejected, interrupted or invalid delta, the firmware clears its ETag and row hashes and
requests a full image on its retry (normally after one second). A partial picture may be visible until that
retry succeeds. The row-table check validates bookkeeping, not a physical readback of the panel. TLS continues
to protect HTTPS traffic; none of its certificate checks change.

**Transfer diagnostics:** every device RGB565 pull with an image logs `Image transfer <device>: <mode>,
full=<M> bytes, payload=<N> bytes, saved=<M-N> bytes (<P>%)`; modes are delta, full image and preview. Savings
have one decimal place and always compare with the full RGB565 image: full images save 0%. Unchanged images
(**304**) come with every poll and are logged at debug level only. Numbers describe the selected response body,
not HTTP/TLS overhead, TCP retransmissions or proof of reception. The next device ETag identifies the accepted
complete image. The device log keeps its events as before (the first image after a start, aborted images); a
successful delta adds no line, so the log is not filled and the flash not written with every image. Hardware
tests are needed to quantify airtime and battery savings.

## Status in the administration UI

| Status | Meaning |
| --- | --- |
| `Waiting for first pull` | paired, no pull yet |
| `Connected` | last pull within three poll intervals, or within two poll intervals after the pull it announced (section 3h) |
| `Updates missing` | no pull for longer than that |
| `Not connected yet` / `Not connected` | web display: no fetch yet / none for three reload intervals (its page is closed) |

`Remove device` deletes the device; its next pull gets **401** and it returns to pairing mode. The device shows `Updates missing` itself after three poll intervals without a successful pull, or two poll
intervals after a longer announced wait.

## Validation

Pairing (correct and wrong code), key hashing, pull authentication, `ETag`/**304**, removal and port separation are covered by Java tests with a local device simulator. The ESP8266 firmware in `vibedock-client/` implements version 2 and runs on real devices.

## Server-side certificate inspection

For the configured external HTTPS address, without an explicit probe override, the server tries:

1. The external hostname using the system resolver.
2. The explicitly configured internal hostname/IP on the **external HTTPS port**. The internal HTTP port is not used; a request-derived administration hostname is not a probe target.
3. A/AAAA records from public resolvers **8.8.8.8** and **1.1.1.1**, deduplicated and limited to eight candidate IPs. The server connects to those IPs on the external HTTPS port.
4. If these routes cannot establish TLS, the existing `crt.sh` fallback can supply a validated root certificate only; it supplies **no leaf pin**. The device must complete its own full certificate check before learning a pin.

This handles local DNS rewrites as well as alternative LAN routes. Public DNS cannot make an unreachable public
port reachable or bypass missing NAT loopback. DNS lookup failures and TLS targets/reasons are logged; successful
public-DNS inspection logs `TLS certificate for … verified through public DNS address …`.

On every live route, **SNI and hostname verification use the original external hostname**, and the chain must be
trusted by Java. A connection to an IP does not change the certificate identity. No HTTP request is required to
inspect the TLS certificate, so there is no HTTP `Host` header. Rejected certificates and wrong hostnames stop the
inspection; public DNS and the certificate log do not supply an unchecked pin.

`EXTERNAL_TLS_PROBE_URL`, e.g. `https://192.168.1.10:10002`, explicitly selects the reverse proxy's LAN **TLS**
listener and takes precedence over the automatic routes. It is a transport override for the configured external
address only. It must not point to the plain HTTP backend. Neither this override nor public DNS changes system
DNS, the device's DNS or the addresses announced to devices.

Both pairing paths include the validated `anchor` and, by default when available, the live certificate's `pin` in
the existing payload. The **Do not send TLS pin** checkbox sets `omitTlsPin=true` in the network pairing form or
USB setup JSON request. It omits only `pin`; `anchor` stays. Missing/false preserves the default for older callers.
Re-pairing replaces an existing device pin; USB **Only pair** does not reinstall firmware. The M1 can start with
the supplied pin, or learn its own after a full check; ESP32 boards currently always use the full check.

The UI shows the external pin status and fingerprint under **Settings → Network**; the pairing forms only offer to leave the pin out.
Successful status inspections are cached for one minute. **Devices → Troubleshooting → Server log** shows the
recent application log, including resolver results, TLS errors and successful public-DNS routes.
